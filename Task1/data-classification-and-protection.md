# Классификация данных, тегирование и меры защиты

## 1. Список данных для защиты

| Данные | Где встречаются (D#) | Категория | Способ защиты | Тег |
| --- | --- | --- | --- | --- |
| ФИО, дата рождения, телефон, e-mail пациента | D1 Patients.xlsx, D2 Journal-Doctor-FIO, D3 карта пациента, D6 бухгалтерия | ПДн (общая категория) | Шифрование at rest (AES-256), контроль доступа RBAC | `PII-BASIC` |
| Адрес прописки, место работы/учёбы | D3 карта пациента | ПДн (общая категория) | Обезличивание при выгрузке в отчёты/аналитику; шифрование at rest | `PII-EXTENDED` |
| Сведения о хронических заболеваниях, диагнозы, назначения, история болезни | D3 карта пациента | Специальная категория ПДн (врачебная тайна, ст. 10 152-ФЗ) | Шифрование at rest и in transit, строгий RBAC (доступ только у лечащего специалиста и пациента), полный аудит доступа | `PHI-SENSITIVE` |
| Результаты лабораторных анализов | D4 RegistryByDate.xlsx, D3 карта пациента | Специальная категория ПДн | Шифрование at rest, обезличивание в реестре за день (замена ФИО на внутренний ID пациента) | `PHI-SENSITIVE` |
| Данные о платежах (сумма, вид услуги, привязка к пациенту) | D5 ККМ, D6 1С:Бухгалтерия | ПДн + финансовые данные | Шифрование канала (TLS/VPN) между ККМ и 1С; в аналитических/BI-выгрузках (где не нужна привязка к конкретному пациенту) — псевдонимизация ФИО на внутренний ID | `FIN-PII` |
| Данные сотрудников (кадровый учёт, зарплата) | D6 1С:Бухгалтерия | ПДн сотрудника | Шифрование at rest, RBAC (доступ только у бухгалтерии и HR) | `PII-HR` |
| Данные о ТМЦ и закупках | D7 1С:Торговля и склад | Коммерческая информация (не ПДн) | Контроль целостности (базовый), доступ по ролям склада/бухгалтерии | `INTERNAL` |
| Учётные данные доступа (домен, AD) | Файловый сервер, KKM-интеграция | Аутентификационные данные | Хранение только хэшей (не паролей), обязательный MFA для доступа к `PHI-SENSITIVE` | `SECRET` |

**Способы защиты, применяемые в проекте:**
- **Шифрование (encryption)** — данные в состоянии `PHI-SENSITIVE` и `FIN-PII` шифруются at rest (AES-256) и in transit (TLS 1.2+/VPN). Подробная стратегия — в Задании 3.
- **Обезличивание (anonymization)** — используется там, где данные нужны для агрегированной аналитики/отчётов и прямая идентификация пациента не требуется (например, реестр анализов за день, отчёты BI).
- **Псевдонимизация/обфускация (pseudonymization)** — используется там, где связь с пациентом нужна системе, но не должна быть очевидна человеку без доп. привилегий (например, замена ФИО на внутренний `patient_id` в логах и промежуточных выгрузках).

## 2. Механизм тегирования данных

Каждому полю/хранилищу присваивается **тег чувствительности**, который движется вместе с данными на всех этапах потока (в схеме БД, в метаданных файла/объекта, в заголовках API-ответов).

### Уровни тегов

| Тег | Описание | Пример данных | Базовые требования |
| --- | --- | --- | --- |
| `PUBLIC` | Не содержит ПДн | Названия услуг, расписание кабинетов | Без ограничений |
| `INTERNAL` | Внутренняя, не персональная информация | Данные ТМЦ, складской учёт | Доступ по домену/роли отдела |
| `PII-BASIC` | Базовые ПДн | ФИО, телефон, e-mail | RBAC + шифрование at rest |
| `PII-EXTENDED` | Расширенные ПДн | Адрес, место работы | RBAC + шифрование + обезличивание в отчётах |
| `PII-HR` | ПДн сотрудников | Кадровые данные, зарплата | RBAC (HR/бухгалтерия) + шифрование |
| `FIN-PII` | Персональные + финансовые данные | Платежи, привязка к пациенту | RBAC + шифрование канала + псевдонимизация в выгрузках |
| `PHI-SENSITIVE` | Специальная категория ПДн (здоровье) | Диагнозы, анализы, история болезни | Строгий RBAC/ABAC, шифрование at rest + in transit, полный аудит, MFA |
| `SECRET` | Учётные данные, ключи, секреты | Пароли, токены, сертификаты | Хранение в Vault/Secret Manager, ротация, MFA |

### Как тегирование внедряется технически

1. **На уровне хранения:** каждый файл/поле в целевой системе (Задание 2) снабжается метаданными тега — либо через колонку `sensitivity_tag` в БД, либо через object-теги в объектном хранилище.
2. **На уровне API:** контракты явно объявляют, какие поля ответа несут какой тег (аннотации в OpenAPI/GraphQL-схеме), чтобы шлюз мог автоматически решать, требуется ли маскирование для конкретного потребителя.
3. **На уровне пайплайна данных:** ETL/интеграционные джобы обязаны переносить тег вместе с данными; правило — «тег не может понизиться без явного шага анонимизации/обезличивания в пайплайне».
4. **Автоматическая проверка:** релиз, который добавляет новое поле без тега или пытается вывести поле с тегом `PHI-SENSITIVE`/`SECRET` наружу без маскирования, блокируется в CI (статический анализ схемы данных) — требование из целевого состояния компании («релиз проверяется в автоматическом режиме на работу с тегированными данными»).

### Инструменты для тегирования (кандидаты)

- **Apache Atlas / OpenMetadata** — каталогизация и тегирование данных в озере данных и хранилищах.
- **AWS Macie / Yandex DataSphere DLP-инструменты** — автоматическое обнаружение и разметка PII в неструктурированных файлах (Excel, сканы) на переходном этапе миграции.
- **Vault (HashiCorp) / Yandex Lockbox** — хранение секретов (`SECRET`) отдельно от бизнес-данных.

## 3. Инструменты, способы и меры обеспечения конфиденциальности по потокам

| Поток (см. DFD) | Мера защиты | Инструмент/технология |
| --- | --- | --- |
| Пациент/Администратор → регистрация ПДн (P1) | Шифрование at rest, валидация минимально необходимого набора полей на входе | TDE (Transparent Data Encryption) БД, JSON Schema-валидация на API-шлюзе |
| Администратор → журнал записи (P2) | RBAC: доступ к журналу только у ресепшена и профильного специалиста | Keycloak/IdP с ролевыми политиками |
| Специалист → медицинская карта (P3–P4) | Строгий ABAC (доступ только к своим пациентам), полный аудит чтения/записи | Политики атрибутного доступа (OPA/Cerbos), Audit Log (ELK/ClickHouse) |
| Лаборатория → результаты анализов (P5–P6) | API-интеграция вместо ручного ввода, подпись и проверка целостности результата | REST/HL7 FHIR API, электронная подпись результата |
| Касса/ККМ → бухгалтерия (P7–P8) | Шифрование канала передачи, отдельный сегмент сети для платёжных данных | TLS 1.2+/VPN, сегментация сети (VLAN/Security Groups) |
| Склад ↔ бухгалтерия (P9) | Ограничение прямого доступа между системами через API-шлюз с журналированием | API Gateway с логированием запросов |
| Все потоки, содержащие `PHI-SENSITIVE`/`SECRET` | Централизованный мониторинг и алертинг при нетипичном доступе | SIEM/Victoria Metrics + Alertmanager (уже есть в стеке компании) |

Обновлённые диаграммы с указанием мер защиты на каждом этапе — в файле `DFD-protected.drawio`.
